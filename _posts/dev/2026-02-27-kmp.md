> **Kotlin Multiplatform(KMP) 환경에서 플랫폼별 네이티브 SDK를 공통 UI 프레임워크인 Compose Multiplatform으로 래핑하는 과정은 단순히 인터페이스를 맞추는 것 이상의 기술적 고민을 필요로 합니다.** 특히 한국 시장에서 필수적인 네이버 지도 SDK를 활용하여 Android와 iOS에서 동일한 선언적 개발 경험을 제공하기 위해 라이브러리를 구축하며 겪은 도전 과제와 트러블슈팅 사례를 정리합니다.

---

## 1. 개발 배경 및 첫 오픈소스 라이브러리 도전

기존의 네이버 지도 SDK는 각 플랫폼의 네이티브 뷰 시스템에 강하게 결합되어 있습니다. Android는 View, iOS는 UIKit 기반의 명령형 API를 사용하므로, KMP 프로젝트의 `commonMain`에서 이를 직접 제어하기에는 구조적 한계가 명확했습니다. 이를 Compose의 상태 관리 시스템과 연결하여 선언적으로 관리할 수 있는 라이브러리의 필요성을 느껴 개발을 시작하게 되었습니다.

특히 이번 프로젝트는 개인적인 활용을 넘어, 누구나 사용할 수 있는 **오픈소스 SDK 라이브러리 형태로 배포하는 첫 시도**였습니다. 배포 규격에 맞는 코드 구조 설계부터 Maven Central 배포까지의 과정을 경험하며, 단순한 기능 구현을 넘어 라이브러리로서의 안정성과 확장성에 대해 깊이 고민할 수 있었습니다.

---

## 2. 주요 기술적 도전

### 명령형 API의 선언적 전환
네이버 지도 SDK는 마커나 경로선 같은 오버레이를 추가할 때 객체를 생성하고 직접 지도 인스턴스에 대입하는 명령형 방식을 따릅니다.
- **해결 방식**: `NaverMapScope`를 설계하고, 컴포저블의 생성과 소멸 시점에 맞춰 `DisposableEffect`를 통해 네이티브 객체의 등록과 해제가 자동으로 이루어지도록 추상화했습니다.

### 플랫폼별 리소스 브릿징 (OverlayImage)
가장 복잡했던 작업 중 하나는 이미지 리소스의 통합 처리였습니다. 특히 iOS에서는 Compose의 `Painter` 리소스를 네이버 지도 SDK가 이해할 수 있는 `UIImage` 형태로 변환해야 했습니다.
- **해결 방식**: `CanvasDrawScope`를 이용해 메모리 상의 `ImageBitmap`에 이미지를 그린 뒤, 이를 다시 `UIImage`로 변환하는 브릿지 로직을 구현했습니다. 이 과정에서 플랫폼 간 밀도(Density) 차이와 좌표계 변환을 정교하게 처리했습니다.

### 개발자 경험 자동화 (Gradle Plugin)
네이버 지도 SDK는 별도의 전용 Maven 저장소 설정을 요구합니다. 라이브러리 사용자가 프로젝트마다 수동으로 저장소 URL을 추가하는 번거로움을 줄이기 위해 `naver-map-compose-gradle-plugin`을 별도로 제작했습니다.

## 3. 주요 트러블슈팅 (Deep Dive)

개발 과정에서 마주한 주요 문제들과 그 해결 과정을 정리합니다.

#### Case 1: Kotlin Native 변환 과정에서의 문서와 실제 동작의 차이
> **현상**: 네이티브 SDK를 Kotlin Native로 변환(`cinterop`)하여 사용하는 과정에서 공식 문서의 설명과 실제 동작이 다른 경우가 다수 발생했습니다.
- **문제**: 특정 API의 리턴 타입이 문서와 다르거나, Objective-C 인터페이스가 Kotlin Native로 변환될 때 예상치 못한 타입으로 매핑되었습니다.
- **대응**: 공식 문서에만 의존하지 않고 실제 생성된 라이브러리 바이너리를 직접 분석하고 테스트하며 적절한 타입을 찾아내는 과정을 거쳤습니다.

#### Case 2: iOS 메모리 참조 및 누수 관리
> **현상**: 초기 개발 단계에서 iOS의 마커 객체가 화면에서 사라진 후에도 메모리에서 해제되지 않는 현상이 발견되었습니다.
- **문제**: Kotlin의 Native Interop 과정에서 발생한 강한 참조 고리(Strong Reference Cycle)가 원인이었습니다.
- **대응**: 오버레이 객체의 `map` 속성에 `null`을 명시적으로 대입하는 로직을 Compose의 `onDispose` 시점에 엄격하게 적용하여 해결했습니다.

#### Case 3: SDK 초기화와 렌더링 시점 동기화
> **현상**: 간헐적으로 지도가 표시되지 않거나 초기화 에러가 발생했습니다.
- **문제**: 네이버 지도는 뷰가 생성되기 전 클라이언트 ID 초기화가 선행되어야 하는데, 초기화 요청과 렌더링 간의 경합 조건(Race Condition)이 발생했습니다.
- **대응**: 초기화 상태를 싱글턴 객체에서 관리하고, 플랫폼별 초기화 로직이 완료된 것을 보장한 뒤 뷰를 노출하도록 실행 순서를 조정했습니다.

## 4. 결론 및 향후 계획

첫 오픈소스 SDK 배포라는 도전 과정에서 플랫폼별 네이티브 SDK의 내부 동작 원리를 깊이 이해할 수 있었습니다. 특히 KMP 환경에서 복잡한 리소스 변환과 메모리 관리, 그리고 **문서와 실제 동작 간의 괴리**를 극복하는 과정은 매우 값진 경험이 되었습니다.

**향후 로드맵:**
1. 마커 클러스터링(Clustering) 기능 추가
2. 더 다양한 커스텀 오버레이 지원
3. 안정성 강화를 위한 유닛 테스트 확충
