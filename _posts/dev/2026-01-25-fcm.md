# [Android/FCM] 알림 서비스 구현 전, 테스트로 시작해 딥다이브까지: FCM 내부 원리 파헤치기

### 0. 시작하며: "그저 테스트 한 번 해보려 했을 뿐인데..."

최근 프로젝트를 진행하며 알림 기능을 넣기 전, FCM(Firebase Cloud Messaging)이 어떻게 돌아가는지 가볍게 테스트를 시작했습니다.

단순히 공식 문서를 보고 코드를 복사해서 붙여넣을 수도 있었지만, 코드 속에 보이는 생소한 어노테이션들과 데이터 흐름을 추적하다 보니 어느덧 **안드로이드의 비동기 처리와 멀티스레드 안정성**을 공부하는 딥다이브 여정이 되었습니다. 그 과정에서 배운 핵심 내용들을 정리해 봅니다.

---

### 1. 코드 속의 숨은 안전장치: @Volatile과 @GuardedBy

Firebase 라이브러리 내부나 싱글톤 패턴을 구현한 `FcmRepositoryImpl`을 분석하다 보면 재미있는 어노테이션들이 등장합니다.

* **`@Volatile`**: 변수의 값을 CPU 캐시가 아닌 **메인 메모리**에서 직접 읽고 쓰게 합니다. 여러 스레드가 동시에 접근할 때 "값의 불일치"를 방지하여, 싱글톤 객체가 중복 생성되는 것을 막아주는 핵심 역할을 합니다.
* **`@GuardedBy("FirebaseMessaging.class")`**: 이 어노테이션은 "이 데이터는 위험하니까 반드시 지정된 자물쇠(Lock)를 소유한 상태에서만 사용해!"라는 뜻입니다. 멀티스레드 환경에서 발생할 수 있는 데이터 오염(Race Condition)을 방지하기 위한 선언적인 안전장치입니다.

---

### 2. 수신대기소 : FirebaseMessagingService

#### (1) FirebaseMessagingService란?

FCM 서버로부터 백그라운드에서 메시지를 수신하고, 토큰이 변경되었을 때 이벤트를 처리하는 안드로이드 서비스(Service) 클래스입니다.
이 클래스는 사용자가 앱을 사용하고 있지 않을 때도(백그라운드 상태) 시스템에 의해 실행되어 메시지를 처리할 수 있게 해줍니다.

#### (2) 핵심 메서드 2가지

```kotlin
class MyFirebaseMessagingService : FirebaseMessagingService() {
    override fun onMessageReceived(remoteMessage: RemoteMessage) {
        val body = remoteMessage.notification?.body ?: remoteMessage.data["body"] ?: "New Message"
        fcmRepository.emitMessage(body)
    }

    override fun onNewToken(token: String) {
        Log.d(TAG, "Refreshed token: $token")
    }
}
```
  
##### `onMessageReceived(remoteMessage: RemoteMessage)`

* **역할:** FCM 서버에서 보낸 메시지가 내 기기에 도착했을 때 호출됩니다.
* **포그라운드(앱 실행 중):** 메시지가 오면 이 메서드가 즉시 호출됩니다. 작성하신 코드처럼 `fcmRepository.emitMessage(body)`를 통해 UI에 바로 뿌려줄 수 있죠.
* **백그라운드(앱 종료/숨김):**
  * **Notification 메시지**: 시스템이 자동으로 알림창을 띄우고, 이 메서드는 호출되지 않을 수 있습니다.
  * **Data 메시지**: 앱이 백그라운드에 있어도 이 메서드가 호출되어 데이터를 처리할 수 있습니다.

##### `onNewToken(token: String)`

* **역할:** 기기의 등록 토큰이 처음 생성되거나, 보안상의 이유로 갱신되었을 때 호출됩니다.
* **지식 포인트:**
  * 토큰은 영구적이지 않습니다. 앱을 지웠다 깔거나, 데이터를 삭제하면 바뀝니다.
  * 실제 서비스라면: 여기서 받은 token을 백엔드 서버(API 서버)로 보내서 저장해야 합니다. 그래야 나중에 서버가 **이 사용자에게 푸시 보내줘**라고 FCM에 요청할 수 있으니까요.

#### (3) 왜 이게 '서비스(Service)'인가요?

안드로이드에서 서비스는 **화면 없이 뒤에서 돌아가는 컴포넌트**입니다.

* 푸시 알림은 사용자가 유튜브를 보든, 게임을 하든, 폰을 꺼두든 상관없이 와야 합니다.
* 따라서 Activity(화면)가 아닌 Service(백그라운드 작업자) 형태를 띠는 것입니다.

### 3. 끊김 없는 이벤트 전달: SharedFlow 전략
메시지를 `UI(Compose/ViewModel)`로 전달하기 위해 `MutableSharedFlow`를 사용했습니다.

```kotlin
    private val _messageFlow = MutableSharedFlow<String>(
        replay = 1,
        onBufferOverflow = BufferOverflow.DROP_OLDEST
    )
```

여기에는 두 가지 전략이 담겨 있습니다.

* 1.`replay = 1`: 사용자가 잠시 화면을 나갔다 돌아와도, 가장 최근에 온 메시지 1개는 놓치지 않고 보여주기 위함입니다.
* `2.DROP_OLDEST`: 메시지가 너무 많이 쏟아질 경우, 성능을 위해 오래된 것은 버리고 가장 최신 것만 유지하는 효율적인 관리 방식입니다.

### 4. 비즈니스 로직의 중심: FcmRepositoryImpl 설계

FCM 서버와 통신하고 데이터를 가공하여 UI로 전달하는 핵심 로직은 `FcmRepositoryImpl`에서 담당합니다. 이 클래스에는 라이브러리 설계의 정석이라 불리는 몇 가지 기법이 적용되어 있습니다.

#### (1) 비동기 Task를 코루틴으로: `await()`의 활용
Firebase SDK의 많은 메서드는 `Task<T>` 기반의 콜백 형태입니다. 이를 현대적인 코틀린 코루틴 환경에서 깔끔하게 다루기 위해 `await()`를 사용했습니다.

```kotlin
override suspend fun getFcmToken(): String {
        return try {
            FirebaseMessaging.getInstance().token.await()
        } catch (e: Exception) {
            "Error: ${e.message}"
        }
    }
```

이 방식은 코드의 가독성을 높일 뿐만 아니라, 비동기 작업 중 에러가 발생했을 때 `try-catch`를 통해 예외 처리를 훨씬 직관적으로 할 수 있게 해줍니다.

#### (2) 안전한 인스턴스 보장: Double-checked locking
Dagger나 Hilt 같은 의존성 주입(DI) 도구가 사용하지 않고 간략하게 앱 전역에서 단 하나의 인스턴스만 보장되도록 **싱글톤 패턴**을 구현했습니다.

```kotlin
    companion object {
        /**
         * DI(의존성 주입) 도구가 완벽히 설정되지 않은 환경을 위한 싱글톤 인스턴스 접근 메서드입니다.
         * Thread-safe한 이중 잠금(Double-checked locking) 패턴을 사용합니다.
         */
        @Volatile
        private var INSTANCE: FcmRepositoryImpl? = null

        fun getInstance(): FcmRepositoryImpl {
            return INSTANCE ?: synchronized(this) {
                INSTANCE ?: FcmRepositoryImpl().also { INSTANCE = it }
            }
        }
    }
```

여기서 사용된 **`@Volatile`**은 여러 CPU 캐시 간의 데이터 불일치를 막고 메인 메모리에서 직접 값을 읽게 하여, 멀티스레드 환경에서도 원자적인 인스턴스 생성을 보장합니다.

#### (3) 관심사의 분리 (SoC)
`FcmRepositoryImpl`은 내부적으로 `MutableSharedFlow`를 통해 메시지를 발행(`emitMessage`)하고, 외부에는 오직 읽기 전용인 `Flow`만 반환(`getMessageFlow`)합니다.
이러한 설계는 UI 레이어(Activity/Compose)가 데이터 발행 로직에 직접 관여하지 못하게 차단하고, 오직 데이터의 변화만 감지하도록 하여 **데이터의 흐름을 단방향(UDA)**으로 유지합니다.
